# Surface routing: identify the product surface first

Read the user's requested product, reference, task, navigation and input context before planning the screen. State the surface in the brief when it affects design. Browser execution, clickability, animation and a narrow screenshot do not determine the category.

| Surface | Main purpose and useful design evidence | Avoid |
| --- | --- | --- |
| Marketing / content website | Reading, exploring or evaluating content; editorial hierarchy, brand, imagery and a relevant next action. Often scroll-led, with responsive content navigation. | Turning content into an operational dashboard merely because it has filters or animation. |
| Mobile app / miniprogram | Repeated handheld tasks; touch targets, one-handed reach, compact navigation, task state, sheets, input and gesture alternatives. Validate a real phone-sized viewport and the intended platform conventions. | Calling a desktop sidebar and KPI grid a phone app; relying on hover or drag alone; assuming every app needs charts. |
| Dashboard / Web UI (browser-based workspace) | Repeated work, monitoring or decision-making; workspace navigation, data hierarchy, tables, filters, status, dense controls and meaningful task feedback. | Confusing dashboard layout with all applications or copying it into a phone flow without restructuring. |

These are routing aids, not fixed templates. A product can contain more than one surface: classify each requested part and preserve the user's scope. A mobile website is still a website when its goal is content exploration; a browser-hosted phone prototype can demonstrate a mobile app flow without being a native app. If a reference is ambiguous, inspect its surrounding screens and describe the assumption rather than silently choosing a category.

Adapt a pattern only after checking that it supports the destination surface. Dashboard examples belong to Web UI, while mobile app examples should demonstrate handheld task flows.
