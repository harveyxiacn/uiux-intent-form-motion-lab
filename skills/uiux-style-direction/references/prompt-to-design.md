# Turn visual prompts into observable design

Use this when a user supplies concrete visual effects or says the result does not resemble a reference. A generic polished style is not an adequate substitute for named composition and motion.

Extract each requested visual into a decision and an observable acceptance condition:

| Request | Design decision | Evidence |
| --- | --- | --- |
| Oversized editorial title | Decide line breaks, relative scale and relation to imagery at each viewport | First-screen screenshot shows title hierarchy without clipping |
| Staggered image composition | Use relevant real assets; specify differing size, alignment and controlled rotation | Images remain legible and do not hide content or controls |
| Ribbon or sticker | Give the motif a role, placement and contrast; keep it subordinate to the page task | Motif appears in the intended composition, not as a generic badge |
| Peel and relocate | Describe corner deformation, lift, travel, destination and settled state | Inspect beginning, intermediate and final states, plus reverse and reduced motion |

Example adapted brief: create a UI portfolio where a large two-line title and four staggered screenshots establish the subject; a small peelable sticker provides one tactile interaction; clear category navigation leads to the live examples below. Use actual project images, not unrelated placeholder photos. This is a particular direction, not a mandatory style for other projects.

Write the brief before code, then compare the render against the individual decisions. Do not substitute a row of neutral cards or a plain embedded viewer merely because all functionality works. Keep an embedded tool useful, but design its surrounding presentation when the user asks for a showcase.

For motion, pair static screenshots with runtime checks. A resting frame alone cannot demonstrate a peel, path or interruption behavior. Record any deliberate simplification explicitly rather than declaring a different effect equivalent.
